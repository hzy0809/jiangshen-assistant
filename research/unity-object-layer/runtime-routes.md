# 将神 Unity/Mono runtime access routes

Status: DONE. This is an offline feasibility result, not proof of a working runtime bridge or successful game-state read. No game process was opened, suspended, injected, hooked, or given input by this analysis. Installed binaries were read without loading them. No client file was modified.

## Result

The least intrusive candidate for **state observation** is a bounded, hash-bound external memory reader that follows existing Mono roots and cached metadata. This route requires neither remote code execution nor a modified client/restart, and the exact installed Mono code now supplies a defensible path from loaded assemblies to already-cached classes and already-initialized ordinary static fields. Live readability, pointer consistency, and business values remain UNVERIFIED here; the controller owns any live experiment.

For **direct button invocation**, exported Mono method APIs are available, but they are in-process APIs. External Python cannot call the game's Mono objects merely by loading mono.dll. A working invocation route additionally requires authorized execution inside that process, correct Unity thread affinity, and a validated business handler. Neither an existing execution bridge nor an enabled debugger endpoint has been established by this leaf. A state reader can support later targeted OS input without providing method invocation.

## Exact offline graph for a later read-only proof

Authoritative evidence for every offset below is the installed binary, pinned by the mono.dll hash above. [runtime-native-disassembly.txt](runtime-native-disassembly.txt), generated by [runtime_disassemble.py](../../tools/runtime_disassemble.py), contains bounded Capstone x86 decoding and raw instruction bytes. [runtime-accessor-bytes.json](runtime-accessor-bytes.json) preserves a separate subset of raw accessor bytes. These offsets are not a portable Mono ABI.

All object pointers are 4 bytes. Resolve the current loaded mono.dll base `B`; do not use the preferred base as a live address. An absolute offline operand `0x101f2584` becomes live `B + 0x1f2584` after relocation.

| Step | Exact installed-code evidence | Read-only interpretation |
|---|---|---|
| Root domain | `mono_get_root_domain` RVA 0x27a1e: `mov eax,[0x101f2584]; ret` | root = u32(B+0x1f2584) |
| Domain enumeration | `mono_domain_foreach` RVA 0x27afe copies a bounded domain array, skips null entries | count=u16(B+0x1f2578); array=u32(B+0x1f2580); domain=u32(array+4*index); do not assume root-domain identity |
| Loaded assemblies | `mono_assembly_foreach` RVA 0x12c77 reads [0x101f23f8], calls helper RVA 0x4ed0 | head = u32(B+0x1f23f8) |
| List walk | Helper 0x4ed0 passes [node] to callback, advances [node+4]; copy helper 0x4f06 allocates 12-byte nodes | node.data = assembly ptr at +0; next at +4; +8 is previous link, unnecessary for read traversal |
| Assembly image | `mono_assembly_get_image` RVA 0x12d17 | image = u32(assembly+0x40) |
| Image name | `mono_image_get_name` RVA 0x16605 | char* = u32(image+0x18); bounded string read |
| Class cache location | TypeDef path RVA 0x17799 calls lookup 0x8ff6 with `lea image+0x2a0` | Cache is embedded at image+0x2a0, not a pointer stored there |
| Cache shape | Initializer 0x8fae and lookup 0x8ff6 | hash callback +0; key callback +4; next-address callback +8; bucket count u32+0xc; entry count u32+0x10; bucket-array ptr+0x14 |
| Callback identity | Image initialization 0x37c6c wires functions 0x2228, 0x37c54, 0x37c5f | Validate these runtime pointers against B+RVA before interpreting cache |
| Token lookup | 0x2228 returns token unchanged; lookup uses unsigned divide by bucket count | bucket_index = TypeDef_token % count; klass = u32(buckets+4*index) |
| Class-chain traversal | 0x37c54 returns [klass+0x38]; 0x37c5f returns address klass+0xa8; lookup dereferences it | key token at +0x38; next klass at +0xa8; bounded bucket walk to exact token |
| Class identity | Name/namespace/parent accessors 0x1659d/0x165a8/0x16570; allocation path writes image+token at 0x17864/0x17868 | name +0x30, namespace +0x34, parent +0x24, image +0x2c, TypeDef token +0x38 |
| Existing field table | `mono_class_get_fields` RVA 0x1a254 advances 0x10 and checks count | field count u32(klass+0x64); array ptr u32(klass+0x74); stride 0x10; consume only if already present |
| Field metadata | `mono_field_get_name` 0x165fa, type 0x274bb, parent 0x3a00f, offset 0x165ef, flags 0x165e1 | field.type ptr+0; name ptr+4; declaring class ptr+8; signed offset+0xc; attrs=u16(typeptr+4) |
| Field type gate | `mono_type_get_type` 0x55f7a, `mono_type_is_byref` 0x55f69, `mono_type_get_class` 0x274bb | enum=u8(typeptr+6); byref=(u32(typeptr+4)>>30)&1; for appropriate CLASS/VALUETYPE enum, declared class=u32(typeptr+0) |
| Existing per-domain vtable | `mono_class_vtable` 0x618fe calls full 0x612d0 | runtime_info=u32(klass+0xa4); domain_id=u32(domain+0x60); require id<=u16(info+0); vtable=u32(info+4+4*id) |
| Vtable domain | `mono_object_get_domain` RVA 0x5f488 reads object.vtable then vtable+8 | require u32(vtable+0)=expected class and u32(vtable+8)=enumerated domain |
| Static initialization complete | `mono_runtime_class_init` 0x62c71 calls full 0x61575; entry 0x6157f checks bit2 at vtable+0x1c; normal completion 0x618b8 checks failure bit4 then sets bit2 | require (u32(vtable+0x1c)&6)==2 before treating static contents as initialized; a nonnull vtable alone is insufficient |
| Ordinary static storage | `mono_field_static_get_value` RVA 0x60f35, ordinary branch 0x60fa1 | require attrs static bit 0x10, literal bit 0x40 clear, offset != -1; field_address=u32(vtable+0xc)+offset |
| Ordinary instance storage | `mono_field_get_value` RVA 0x5eea1, branch 0x5eef5 | require nonstatic; field_address=managed_object+field.offset |
| Instance type | `mono_object_get_class` RVA 0x5f495 | vtable=u32(obj); klass=u32(vtable) |

This graph avoids invoking `mono_class_get`, `mono_class_from_name`, `mono_class_vtable`, or `mono_class_get_fields`; those functions can initialize missing metadata/storage. A null or missing cache, field table, runtime_info, vtable, static-data pointer, or unrecognized special field is a stop/UNVERIFIED condition, not permission to initialize it. `mono_class_vtable_full` explicitly falls back to construction when cached data is absent.

The legacy Mono 2.6.7 headers corroborate the meanings of these already-disassembled fields: MonoVTable domain/data and initialized/init_failed flags, and signature enum values BOOLEAN=0x02, I4=0x08, U4=0x09, R4=0x0c, R8=0x0d, VALUETYPE=0x11, CLASS=0x12. That reference version is not asserted to be the installed runtime; installed code controls offsets. [Legacy MonoVTable definition](https://raw.githubusercontent.com/mono/mono/mono-2-6-7/mono/metadata/class-internals.h), [legacy MonoTypeEnum](https://raw.githubusercontent.com/mono/mono/mono-2-6-7/mono/metadata/blob.h).

The native graph permits **already cached ordinary TypeDefs**, not every possible generic/array/dynamic type. Use the other analyst's offline metadata tokens and field declarations to select exact business roots. Do not enumerate arbitrary heap regions or infer fields from unrelated modern Mono layouts. External reads do not take Mono's internal locks; repeated reads can reveal changes but cannot guarantee an atomic game snapshot.

Important counterexample: js.exe itself exports names such as `mono_runtime_invoke`, but their export RVAs target zero-initialized `.data` slots beyond that section's on-disk raw data. They are not exported function implementations and must not be disassembled/called as code. The inventory marks them `file_backed: false`. Use the actual loaded mono.dll export table and its code.

## In-process API and Unity-thread requirements

Confirmed Mono exports include domain enumeration, assembly enumeration, class/method/field lookup, GC handles, `mono_thread_attach`, `mono_thread_detach`, `mono_runtime_invoke`, and `mono_domain_assembly_open`. The installed x86 wrapper/caller code shows caller-managed stack arguments and plain `ret`, consistent with the legacy cdecl C embedding interface. A future helper must declare exact signatures, 32-bit pointers, return types, callback conventions, exception out-pointers, and value/reference parameter handling; export presence alone does not verify an adapter.

Useful signatures from the embedding interface include `MonoObject* mono_runtime_invoke(MonoMethod*, void* this_object, void** args, MonoObject** exception)` and `MonoThread* mono_thread_attach(MonoDomain*)`. An externally created thread must attach before Mono API/object access. Attach registers it with Mono; it does not move it to Unity's main thread. Do not call `mono_jit_init`/cleanup to create/destroy a second runtime in the already hosted game. [Mono embedding/threading guidance](https://www.mono-project.com/docs/advanced/embedding/).

Exact installed UnityEngine evidence:

- [runtime-UnityEngine.Object.cs](runtime-UnityEngine.Object.cs): `FindObjectsOfType(Type)`, `FindSceneObjectsOfType(Type)` and native-backed object methods exist. Its private backing field is `ReferenceData`, not the modern assumed `m_CachedPtr` field.
- [runtime-UnityEngine.ReferenceData.cs](runtime-UnityEngine.ReferenceData.cs): `instanceID:int`, `cachedPtr:IntPtr`.
- [runtime-UnityEngine.Resources.cs](runtime-UnityEngine.Resources.cs): `Resources.FindObjectsOfTypeAll(Type)` exists as an InternalCall.
- [runtime-UnityEngine.GameObject.cs](runtime-UnityEngine.GameObject.cs): `AddComponent(Type)` and `SendMessage` exist.
- [runtime-UnityEngine.MonoBehaviour.cs](runtime-UnityEngine.MonoBehaviour.cs): `Invoke`, `InvokeRepeating`, `StartCoroutine` exist.
- [runtime-UnityEngine.classes.txt](runtime-UnityEngine.classes.txt): no `UnitySynchronizationContext` or `RuntimeInitializeOnLoadMethodAttribute` class found in this installed UnityEngine. Modern startup/context recipes are unverified for this version.

An authorized in-process helper would need an initial **verified main-thread callback** to create/register a component or bind an existing validated queue; a helper component can then drain a bounded queue in `Update`. Unity 4.1 documents that `Update` runs every frame for enabled MonoBehaviours. `Invoke`, `StartCoroutine`, `AddComponent`, and `SendMessage` are engine calls, not proof of a safe way to bootstrap from an arbitrary foreign thread. `mono_thread_set_main` must not be treated as a dispatcher. [Unity 4.1 Update](https://docs.unity3d.com/410/Documentation/ScriptReference/MonoBehaviour.Update.html).

For a future enumeration proof, request one specific UI/component type and bound its output. `Resources.FindObjectsOfTypeAll` also includes disabled/internal objects and assets; Unity 4.1 warns it is slow. It requires filtering to live scene objects before any later UI action. The method itself would execute code and allocate results, so it is outside a VM_READ-only proof. [Unity 4.1 object enumeration](https://docs.unity3d.com/410/Documentation/ScriptReference/Resources.FindObjectsOfTypeAll.html).

## Minimal next experiment and stop conditions

The controller can review a separate external reader before authorizing execution. Its first stage should use only query/read rights, pin the loaded x86 module and on-disk hash, verify accessor bytes/relocations, read the two global root slots, and enumerate a capped assembly-name list. It should stop on invalid address/size, changed module identity, cyclic chains, excessive counts, or partial reads. Do not request VM_WRITE, VM_OPERATION, thread creation, suspend, or debugger access for that stage.

If that passes, the next bounded stage is one exact cached business TypeDef token, its expected name/namespace/image, an existing field table, and one already-initialized ordinary static reference. Enumerate domains instead of assuming the root domain; require the vtable's own domain pointer and initialization-complete/failure-clear flags to agree. Validate the reference's declared type, dynamic type and domain through object→vtable→class/domain. Only after a metadata/value schema is fixed should a small allowlisted primitive/button-state snapshot be attempted. Avoid reading unrelated strings, configuration, credentials, arbitrary object graphs, or full dumps. A successful root/assembly probe does not establish business field correctness.

A direct invocation proof would be a separate decision: select the precise in-process entry, main-thread bootstrap, managed profile, transport, one-shot read-only handler, lifecycle/disable mechanism and restart-based cleanup plan. Adding/removing a MonoBehaviour is reversible state change; an assembly loaded into Unity's default domain is not generally removed by simply deleting its file. No such payload was built or loaded here.
